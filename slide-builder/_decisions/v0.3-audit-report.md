# Planted-failure probes

## Probe A — body_top_y_px = None on body-canonical layout — CAUGHT
Built a synthetic LayoutChrome with layout_class=body-canonical and body_top_y_px=None.
`twins.helpers.body_zone_for_chrome` raises `ChromeSidecarMissingError` with the
recovery command embedded ("Re-register the template (register_template.py propose
-> commit)"). No silent fallback.

## Probe B — body_overlay_hex = 'XYZ' (non-hex) — CAUGHT (with caveat)
`twins.composer._insert_dark_overlay` raises `ValueError` immediately on a malformed
hex string: "body_overlay_hex must be 6-char hex; got 'XYZ'". The helper-level catch
is loud.

**Caveat:** at the higher level, `finalize_deck._apply_body_canonical_finishing` is
wrapped in a broad try/except (lines 1082-1088 of finalize_deck.py) that downgrades
ALL exceptions from the body-canonical finishing path to a stderr WARN. A bad
overlay hex would surface as a warning, not a hard build failure. This is consistent
with the v0.2 "don't break the graft for a finishing-only issue" stance but it does
soften the loud-fail contract for this specific path. Flagged as Unresolved Concern
#1 below — not a v0.3 regression (the try/except is part of v0.3 by design).

## Probe C — sha8 drift in chrome.yml — CAUGHT
Copied OTC template + chrome.yml to a temp dir, set source_template_sha8='deadbeef',
called `finalize_deck._load_and_verify_chrome`. Raises `RuntimeError` with the full
mismatch context and the recovery command. Confirmed by contract check
`sidecar freshness: sha8 mismatch hard-fails finalize_deck`.

# Unresolved concerns

1. **Broad except in `_apply_body_canonical_finishing` (finalize_deck.py:1082-1088).**
   Any exception from the body-canonical post-graft finishing (overlay insert OR
   placeholder population) is swallowed as a stderr WARN. A bad body_overlay_hex,
   a missing inherited placeholder, or any other finishing failure produces a
   warning rather than a build-stop. Argument for keeping it: the grafted slide is
   still structurally valid even if finishing fails; QC will catch downstream.
   Argument for removing it: Probe B's ValueError contract is softened. Recommend
   tightening to catch only the specific known-recoverable failures rather than
   blanket Exception. Not a blocker — the helper-level raises are still correct.

2. **Stale smoke build artifact (slide_03/option_A.pptx).** The smoke build last
   ran at 2026-05-28T17:21:54 against an earlier state of OTC chrome.yml (modified
   2026-05-28T21:44:25 when Mario added `body_overlay_hex` to Layout 01 and
   changed `Use as default slide template_subtitle` to layout_class=bespoke). The
   slide_03 artifact still carries a populated Title 1 placeholder consistent with
   the older body-canonical classification. Re-running graft_and_theme with the
   current chrome.yml on the same raw input produces the correct bespoke output
   (no Title 1 placeholder). This is a workflow-hygiene issue, not a code defect.
   Recommend bumping the smoke build's chrome sha into a marker file so a stale
   artifact is loud, or having finalize_deck re-write the smoke when chrome.yml
   changes.

3. **Pattern-author text color on overlay-painted slides.** Mario's example slide 2
   (funnel pattern) shows dark text rendered on top of the dark overlay because the
   pattern code passes literal `color=TEXT_DARK` to `add_text`. The chrome
   correctly carries `text_role: light_on_dark` and `add_title_block` correctly
   flips the title to white. The defect is in pattern-author code (smoke build's
   option_A.py and Mario's funnel pattern), not in v0.3 layout inheritance.
   Advisory: pattern templates should source body text color from
   `_text_colors_for(chrome.text_role)` rather than literal `TEXT_DARK`. Out of
   scope for v0.3 audit but worth tracking.

4. **Implementer claim discrepancy — `add_footer` is not a full no-op on
   body-canonical v2.** The v0.3 blocker doc claims `add_footer` "no-ops on
   body-canonical v2 chrome". In fact, `add_footer` only suppresses the
   page-number on body-canonical v2; footnote + source text are still drawn at
   canonical positions. This matches the v0.2 design lock (footnote/source are
   user-fillable invariant-zone content, not chrome) — the claim was imprecise,
   the implementation is correct.

# Recommendation

**Proceed to merge.** v0.3 fixes the user-facing body-canonical layout-inheritance
bug Mario reported in v0.2. The loud-fail contracts hold for missing geometry, bad
hex, and sha8 drift. Visual verification against both OTC (chrome-rich) and FDX
(chrome-less) real templates confirms the inheritance + overlay paths render
correctly. The four unresolved concerns above are non-blocking: #1 (broad except)
is a hardening item to track for v0.4; #2 (stale smoke artifact) is a workflow
hygiene issue; #3 (overlay text color) is a pattern-author concern outside the
layout-inheritance scope; #4 (footer claim) is a doc imprecision.
