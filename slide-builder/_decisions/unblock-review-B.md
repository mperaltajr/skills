## Verdict on Path α / β / γ

**Recommend β with one amendment, NOT α.**

Path α ("install mmdc + register template + retry, ~45-60 min") looks cheap but conceals a contract break the reviewer-A timing lens cannot see:

- v2's `build_deck.py::generate_mermaid_theme()` (lines 499-559) reads **the OLD shape** — it walks dotted paths like `("colors", "dk2")` and `("fonts", "minor")` against a `template.json` discovered by `find_template_json()` (lines 473-496).
- v1's new `register_template.py` writes **a different shape** — `<stem>.theme.json` with a top-level `brand` dict (`primary_hex`, `accent_hex`, `cover_bg_hex`, `font_heading`, `font_body`) plus an `extracted.all_colors` sub-dict (lines 700-720 of register_template.py).
- These files do not share a key. `_lookup(theme_json, ("colors", "dk2"))` against v1's `.theme.json` returns `None` for every slot — every entry falls back to the hardcoded FedEx-purple defaults in `THEME_MAPPING` (build_deck.py lines 85-108).

So if Mario runs α without an adapter, v2 will silently re-generate a FedEx Mermaid theme for **every client** because the lookup is universally missing. The current `mermaid-fedex.json` on disk already proves this — its `_comment_fallbacks_used` array has 17 entries all stamped `"(no template.json)"`. The Stage 3 smoke ran with **zero** real template-derived values; v2 has never actually exercised the mapping. That's the latent defect Path α would lock in.

Path γ (mmdc-only, halt on registration) preserves correctness but stops Item 1. Path β (halt + document + resume) is the only path that doesn't ship a known-broken adapter into production. **Amendment:** Stage 2 of β must include writing the `theme.json → themeVariables` adapter in `build_deck.py`, not just installing mmdc.

## Exact technical order of operations

The dependency DAG (read top-to-bottom; each step depends only on what's above):

1. **Install mmdc globally.** No code change. Independent of templates. `npm install -g @mermaid-js/mermaid-cli@11.4.0`. Verify with `mmdc --version`. This is the only step that can run in isolation safely.

2. **Delete the stale `theme/mermaid-fedex.json` cache.** It was generated by v2's current `generate_mermaid_theme()` against the OLD convention with all-fallback values. Leaving it on disk means a future smoke re-uses a wrong-by-design file (build_deck.py recomputes it on every run, but partial-failure paths or `--theme` flags can pick up the stale one).

3. **Patch `build_deck.py::generate_mermaid_theme()` to read v1's new `.theme.json` shape.** This is the cross-stream contract fix (see § "Schema-mismatch risk" below). It MUST land before any non-FedEx template registers, because once a template is registered v2's loader will silently mis-map it.

4. **Register the FedEx template via v1's `register_template.py`** — but NOT with `--auto-accept-phase1`. See § "v1's `register_template.py` smoke status" warning below. Mario must drive Phase 3 to correct the orange/purple inversion.

5. **Verify `BrandSidecarMissing` no longer raises** by running `finalize_deck.py --skip-build` against the existing slides 1+4 artifacts.

6. **Re-dispatch slides 1+4** (see § "Risk: stale artifacts vs fresh dispatch"). The existing `option_X.pptx` files cannot be reused as-is.

7. **Resume Item 1 smoke at Stage 3.**

Answering the sub-questions directly:

- (a) **mmdc first, then registration.** mmdc has zero dependency on anything in the theme pipeline; it's a missing binary, not a contract problem. Front-load it.
- (b) **`generate_mermaid_theme()` update lands BEFORE Mario registers FedEx.** If registration happens first, v2's loader will succeed (no crash, no warning) but produce the wrong Mermaid theme on every subsequent run.
- (c) **`register_template.py` MUST run before `build_deck.py` can write a correct per-deck `mermaid-<slug>.json`.** Today `build_deck.py` walks `find_template_json()` looking for the OLD `template.json`; until it's patched to read `<stem>.theme.json`, it can't see registration output at all.
- (d) **Yes, there's a cache interaction.** `mermaid-fedex.json` exists on disk and was generated against the old convention with 17 hardcoded fallbacks. Either delete it (Step 2 above) or accept that v2 will regenerate it correctly only AFTER the build_deck.py patch lands.

## Risk: stale artifacts vs fresh dispatch

Slides 1+4 have `option_X.pptx` files on disk from agent dispatch. The question is whether `finalize_deck.py` can graft and theme them post-registration.

**The raw pre-theme PPTX files in `_raw/option_X.pptx` are theme-agnostic** — agents produce them using Slide Lab default hexes (`460073` purple, `A100FF` electric purple, etc. — see `client_theme.py` lines 70-81 for the literal list). So the raw bytes are reusable.

**But the themed `option_X.pptx` files at the top level of each `slide_NN/` were produced by `apply_theme_to_shape_xml()`** against whatever color_map was active at dispatch time. Two scenarios:

1. If the dispatch ran BEFORE v1's theme rewrite shipped, the themed files were built with the OLD loader's color_map → wrong colors baked in.
2. If they were built but `finalize_deck.py` crashed at `load_client_theme()` before theming, only raw files exist.

Either way, the safer move is: **discard the top-level themed `option_X.pptx`, keep `_raw/option_X.pptx`, re-run `finalize_deck.py --skip-build` to regraft+retheme from raw**. `--skip-build` (defined at finalize_deck.py line 841) does exactly this — it skips the `option_X.py` execution and uses existing PPTX. No agent re-dispatch needed if `_raw/` is intact. If `_raw/` is missing for any slide, that slide DOES need re-dispatch.

## Schema-mismatch risk (template.json → .theme.json transition)

This is the biggest hidden risk. Concrete diff:

**Old `template.json` (what v2 currently expects):**

    { "colors": { "dk1": "...", "dk2": "4D148C", "lt2": "FF6600", ... },
      "fonts":  { "major": "...", "minor": "FedEx Sans Regular" } }

**New `<stem>.theme.json` (what v1 now writes — register_template.py lines 700-720):**

    { "schema_version": 1, "template_path": "...", "template_sha": "...",
      "brand": { "primary_hex": "#4D148C", "accent_hex": "#FF6600",
                 "cover_bg_hex": "...", "font_heading": "...", "font_body": "..." },
      "extracted": { "all_colors": { "dk1": "...", "dk2": "4D148C", ... },
                     "all_fonts": { "heading": "...", "body": "..." } } }

The raw `all_colors` palette IS still there under `extracted.all_colors`, so v2's existing 17-slot mapping could be salvaged by changing `_lookup()` paths from `("colors", "dk2")` to `("extracted", "all_colors", "dk2")`. **But that's the wrong fix** — it reintroduces the slot-position guessing that v1 just deleted (see `client_theme.py` lines 4-9 which explicitly retire `_pick_brand_colors`, `_pick_primary_mid`, `_pick_accent_soft` etc.). The right fix is to read `brand.primary_hex` and `brand.accent_hex` directly and derive the rest mechanically (mirror `client_theme.py::color_map()` lines 271-328).

Minimal correct patch in `build_deck.py::generate_mermaid_theme()`: replace the `THEME_MAPPING`-driven lookup with a direct read of `brand.primary_hex` (→ `primaryColor`, `primaryBorderColor`, `lineColor`, `nodeBorder`, `defaultLinkColor`) and `brand.accent_hex` (→ `secondaryColor`, `secondaryBorderColor`). Leave `tertiary*`/`mainBkg`/`clusterBkg`/`edgeLabelBackground` as fixed neutrals. **This update IS v0-blocking** — without it, every non-FedEx Mermaid render ships FedEx purple, defeating per-client theming.

## Biggest concern

**The `register_template.py` FedEx smoke produced inverted colors (orange-as-primary, purple-as-accent), per v1's recent report, and Mario has not yet driven Phase 3 to correct it.** If Mario runs Step 4 above with `--auto-accept-phase1`, v1's `_best_guess_primary_accent()` (register_template.py lines 265-324) will write `brand.yml` with the inversion baked in. The downstream chain — `client_theme.color_map()` for native theming AND v2's new `generate_mermaid_theme()` for Mermaid — will both faithfully propagate the inversion across the whole deck.

`build_deck.py::validate_theme()` has a `KNOWN_CLIENT_HUE_RANGES` check for FedEx (lines 587-592) requiring primary hue 260-310° (purple). If `brand.yml` says primary is `#FF6600` (orange, hue ~24°), Check 3 will fire and halt the build. So v2 IS protected against the inversion landing silently — but only because Mario added FedEx to the hue-range table. Any other client (NFL, ACN) registered with auto-accept and the same best-guess bug would pass v2's structural checks (primary != accent, plausible saturation) and ship with wrong colors anyway. The validate_theme warning at lines 737-747 ("client not in KNOWN_CLIENT_HUE_RANGES") would be the only signal, and it is a warning not an error.

**Mandatory:** Mario must register FedEx in interactive mode (no `--auto-accept-phase1`), eyeball the smoke PNG, swap primary/accent in Phase 3, and confirm via the TTY gate. Only then is Step 5 safe to run.
