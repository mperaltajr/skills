## Unresolved concerns

1. **Content-stripping bug (highest priority)**: `_apply_body_canonical_finishing` on the dark path strips ALL slide shapes via `_strip_layout_placeholders`, not just the inherited layout placeholders. This is the root cause of both Test 4 and Test 7 failures. The dark-variant feature ships an empty slide and the collision gate sees nothing to flag.

2. **Title-resolution side effect**: The white title that `_apply_body_canonical_finishing` draws on top reads `src_slide` for a shape named `title` or starting with `title`. With the worker option_A.py's `add_title_block(slide, "...")`, the title shape is named `Title 1` (capital T) and the lowercase-match check (`name == "title" or name.startswith("title")`) does match (`name.lower()` is computed first — re-check). Actually, looking at lines 989-997, `name = (shape.name or "").strip().lower()` IS lowercased before the check, so it does match. The title that ends up on screen is the brief's first-line title ("Dark funnel"), not the body-field `**Slide title:**` ("Where the cash gets stuck — the funnel"). This is because `add_title_block` uses whatever text was passed; in this audit the option_A.py used the brief's `**Slide title:**` value, so the appearance of "Dark funnel" must trace to a different path. Worth a closer look but secondary to the strip bug.

3. **Collision-check ordering is inherently brittle**: even after the strip bug is fixed, the collision check must inspect the FINAL composed slide (post-graft, post-overlay, post-strip) for shapes whose original-XML hex collides with dark_bg. Today it runs on the post-strip slide. Either move the check to BEFORE `_apply_body_canonical_finishing`'s strip (inspect raw grafted content + then drop overlay-only shapes), or stop stripping grafted content in the first place.

4. **Theme-remap interaction**: the collision detector walks the slide AFTER `apply_theme_to_shape_xml` would normally rewrite colors. The detector runs INSIDE `graft_and_theme` BEFORE the theme remap (line 1291 vs 1303), so it sees Slide-Lab-literal hexes, not client-remapped hexes. But finalize compares against `dark_bg_hex` (client-side). On a fresh OTC build the literals 460073 / A100FF would NOT collide with 4D148C until they're remapped to 4D148C. Workers using literal helpers.py colors will only be detected for collisions AFTER the remap, but the detector ran before. (In Test 7 we hardcoded RGB(0x4D,0x14,0x8C) into the option script, so it bypassed the remap and the unit detector caught it — that's why the unit test passes but the integration test fails for a *different* reason than expected.)

5. **`_apply_body_canonical_finishing` exception handling swallows the strip-induced damage**: the try/except at line 1294-1300 of finalize_deck.py prints a warn but does not surface the empty-slide outcome. Even if the strip were fixed, this should hard-fail rather than warn.

## Recommendation

**Do not merge.** Fix the content-stripping bug first, then re-audit. Specific fixes needed before this can be `audit-confirmed`:

a. In `_apply_body_canonical_finishing` dark path, do NOT call `_strip_layout_placeholders` over the already-grafted shapes. Instead, strip ONLY the inherited layout placeholders BEFORE the graft loop appends source shapes — i.e. move the dark-path strip up into `graft_and_theme` at the same place the non-body-canonical strip happens (line 1237), gated on `_is_dark`. Then the overlay can be inserted (at z-order 2, above layout chrome, BELOW the grafted source content) without trampling the source content.

b. Make the collision check loud about its inputs: log how many shapes it walked, with their hex values, in verbose mode. Right now it silently returns 0 when the slide is empty.

c. Add an integration test under `slide-builder/tests/` that asserts:
   - dark variant produces a themed slide with grafted shape count >= source shape count + 1 (overlay) + 1 (title) — i.e., source shapes are not lost.
   - colliding dark content actually raises `DarkVariantCollisionError`.

d. Consider running the collision detector on the FINAL post-theme XML (the actual hex bytes that will hit the renderer) rather than python-pptx's high-level fill/font API. That removes the literal-vs-remapped ambiguity and makes the check authoritative.

The unit-level pieces (collision math, threshold, false-positive guard, brand.yml round-trip, picker JSON) are all correct. The end-to-end wiring is broken at one specific point — `_strip_layout_placeholders` being indiscriminate when called from the dark-finishing path — and that single defect breaks the two most important guarantees the feature is supposed to make.
